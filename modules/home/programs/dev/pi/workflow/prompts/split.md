把规格「$1」发布为主 issue，并拆分为 sub issue。本流程禁止编写实现代码。

## 发布主 issue

读取规格文档：用户通过参数提供路径时读取 `$1`；否则在 `docs/specs/` 下查找本次工作对应的规格，或者从当前对话确定。用 `gh issue create` 创建主 issue，标题使用规格主题，正文使用规格文档的完整内容。创建成功后把主 issue 编号回写到规格文档头部，格式为 `> 主 issue: #<编号>`。

## 垂直拆分

把规格拆成 tracer-bullet 垂直切片，切片必须满足：

- 贯穿全部层次，是垂直切片，不是某一层的水平切片。
- 可以独立演示或者验证。
- 可以放进一个全新的上下文窗口完成。
- 验收标准落到规格「测试决策」声明的 seam 上；拆分方案中注明每个切片覆盖的 seam。

切片的标题与描述使用项目的领域术语表词汇，遵守涉及区域的 ADR。主动寻找 prefactor 机会：先让改动容易，再做容易的改动；prefactor 排在切片最前。

**宽重构是垂直切片的例外。** 宽重构是单一机械改动（重命名列、修改共享符号类型）而爆炸半径横扫整个代码库，单一编辑同时破坏数千个调用点，无法以垂直切片落地。此时按 expand–contract 排序：先 expand，把新形态放在旧形态旁边，一切照旧工作；再按爆炸半径分批迁移调用点（按包、按目录），每批一张切片，全部被 expand 阻塞，批次之间保持检查通过，因为旧形态仍然存在；最后 contract，在没有调用者剩余之后删除旧形态，一张切片被所有迁移批次阻塞。当批次也无法单独保持通过时，保留该顺序，但让所有批次共享一个集成分支，共同阻塞一张最终的集成验证切片，「通过」只承诺在那里成立。

阻塞关系用 GitHub 原生关系表达，不用正文描述。

## 确认拆分

把拆分方案作为编号列表呈给用户，每条包含标题、阻塞它的切片、交付的行为。询问用户：粒度是否合适；阻塞关系是否正确；是否需要合并或者继续拆分。迭代到用户确认之后再发布。

## 发布 sub issue

按依赖顺序发布，先发布被依赖的切片，使阻塞关系可以引用真实编号。每条使用 `gh issue create --parent <主 issue 编号> --blocked-by <编号列表>`；正文使用以下三段结构，使用原生阻塞边时不写 Blocked by 段：

```markdown
## Parent

主 issue 的引用。

## What to build

本切片从用户视角交付的端到端行为，不是逐层实现清单。

## Acceptance criteria

- [ ] 标准 1
- [ ] 标准 2
```

正文禁止写具体文件路径或者代码片段——它们很快失效。唯一例外：原型产出的片段比散文更精确地编码了决策（状态机、reducer、schema、类型形态）时，内联该片段并简要注明来自原型，只保留决策密集的部分，不是可运行演示。标签使用 `ready-for-agent`，仓库中没有该标签时用 `gh label create` 先创建。

禁止关闭或者修改主 issue。完成后报告主 issue 与全部 sub issue 的编号与标题。
