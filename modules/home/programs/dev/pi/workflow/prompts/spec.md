与用户完成「$@」的需求定义，产出规格文档。本流程禁止编写实现代码。

## 追问

加载 grilling skill 并遵循其方法：把需求视为一棵决策树，按轮次提出当前前沿的全部问题，每个问题编号并附上推荐答案，等待用户回答后推进下一轮。需要查证的事实时，使用 subagent 工具派遣 scout（代码调研）或者 researcher（外部资料），禁止向用户索要可以自行查证的信息。追问过程中同步维护共享语言：新确立的领域术语写入仓库的术语表（如 `docs/glossary.md`，不存在时创建），影响后续设计的取舍写入 `docs/adr/` 的新 ADR，随共识同步更新，不留到产出阶段。前沿清空之后，请用户确认已经达成共识。

## 原型

某个关键设计决策（接口形态、状态机、数据模型）用文字无法确定时，先构建一次性原型回答该问题，把结论写回追问记录，再继续。原型只回答设计问题，不进入交付代码。

## 产出

共识达成后，将规格写入 `docs/specs/<主题>.md`（目录不存在时创建，文件名使用英文小写连字符），包含：

- 问题陈述：从用户视角描述要解决的问题
- 目标与非目标
- 用户故事：编号列表，覆盖功能的全部方面
- 实现决策：模块划分、接口形态、架构取舍，不写具体代码与文件路径
- 测试决策：明确列出本规格的测试 seam（公开边界）清单，每个 seam 注明它防止什么、漏什么；测试哪些模块、验收标准、参照仓库中的哪些既有测试。seam 越少越好，理想数量是一个
- 约束与依赖

写完后请用户审阅并确认。这份文档是 `/split` 的输入，必须完整、明确，每条要求都可以验证：`/split` 把它发布为主 issue，并按垂直切片拆出 sub issue，主 issue 是 `/start-work` 的唯一实施依据。
