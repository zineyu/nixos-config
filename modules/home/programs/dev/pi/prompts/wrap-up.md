description: 交付：使文档与代码的最终状态一致，推送分支并创建 PR
argument-hint: "[sub issue 编号或者 URL]"
---

对照本次改动的最终状态，检查并更新仓库文档：

1. `README.md`：安装方式、使用方式、功能清单如有变化则更新。
2. `AGENTS.md` 及各层级的说明文件：目录结构、模块职责、工作流程、命令入口如有变化则更新。
3. `docs/`：架构决策新增或者变更时，在 `docs/adr/` 添加新的 ADR（已有 ADR 的正文保持不动，新的决策写入新文件）；手册与速查表保持同步。
4. 代码注释：与实现保持一致，删除失效注释。

文档只描述最终状态，禁止保留“之前是 A，现在改为 B”这类变更记录，历史由版本控制管理。删除已经失效的内容，禁止补丁式堆积。

## 检查与验收

1. 运行仓库规定的格式化、静态检查与测试，全部通过之后再继续。仓库没有定义这些检查时，运行覆盖改动的最小验证集合。
2. 用 `gh issue view` 读取本次的 sub issue 与它的 `parent`（主 issue）：主 issue 的正文是规格，sub issue 的验收标准是本次的实施范围。用户通过参数提供编号或者 URL 时读取 `$1`；否则从当前对话确定；仍无法确定时询问用户。
3. 对照验收标准逐条核对，勾选已经满足的验收项，把欠妥的地方在 sub issue 上注明。存在未满足的验收项时禁止创建 PR，向用户报告该验收项与原因。

## 创建 PR

1. 从仓库说明（`AGENTS.md`、`README.md`、`docs/`）读取默认分支、检查命令与交付方式；没有记录时询问用户。
2. 在专用分支上提交改动并推送。分支命名使用 `<sub issue 编号>-<主题 slug>`。禁止直接推送到默认分支。
3. 用 `gh pr create --base <默认分支> --head <分支>` 创建 PR。标题使用 sub issue 的标题，正文使用下列四段：

   - 关联：`Closes #<sub issue 编号>`
   - 改动清单
   - 验证结论：规格方向与标准方向各自的结论
   - 遗留问题

   正文只描述最终状态，禁止写入实现思路与过程记录。
4. 用 `gh pr edit --add-reviewer <login>` 请求评审。reviewer 来源按仓库说明或者用户指定；无法确定时询问用户。
5. 在 sub issue 上注释 PR 编号或者 URL、改动清单、验证结论与遗留问题。禁止关闭或者修改 sub issue，它由合并关闭。禁止修改或者关闭主 issue。

## 报告

报告 PR 编号与 URL、更新的文件清单、检查命令与结果、未满足的验收项。

说明下一步：评审有意见或者检查失败时运行 `/pr-review`；PR 合并或者关闭之后运行 `/close-out`。

本流程禁止合并 PR，禁止关闭 PR。
