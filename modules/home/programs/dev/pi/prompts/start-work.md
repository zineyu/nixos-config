## 读取规格

实施之前，规格必须已经确定。用户通过参数提供编号或者 URL 时读取 `$1`；否则从当前对话确定本次工作的 sub issue，仍无法确定时询问用户。用 `gh issue view` 读取该 sub issue，并用它的 `parent` 字段定位主 issue：主 issue 的正文是规格，sub issue 的验收标准是本次实施范围。规格缺失时先补齐主 issue。规格已经确定之前，禁止修改任何实现代码。

## 按照规格实施

你是首席程序员：架构决策、跨模块设计、核心代码由你亲自完成，禁止委派。实施范围限于该 sub issue；需要变更规格或者超出范围时，先与用户更新主 issue 或者 sub issue，再修改代码。

委派规则（外科手术团队模型）：

- 只委派规格可以一次写清、结果可以独立验证的工作：scout 负责代码调研，researcher 负责外部资料，worker 负责边界清晰的实现块。
- 给每个 subagent 最小必要上下文；它的最终消息是精炼结论，直接依据结论行动，无需亲自重读全部原始内容。
- subagent 之间禁止横向协商，你是唯一的汇总点。

## 独立验证

实施开始之前记录当时的提交作为固定点，验证范围是固定点到当前工作区之间的全部改动；这条比较命令确定一次，交给两个 verifier 使用。

加载 code-review skill 并遵循其方法，沿两个方向并行派遣两个 verifier，使双方的上下文互不污染：

- **规格方向**：给出主 issue 与 sub issue 的编号以及改动范围，由它依据规格编写并运行测试。要求它报告：规格提出但缺失或者只完成一部分的要求；改动中出现而规格未提出的行为；看似完成然而实现有误的要求。每条结论引用规格原文。
- **标准方向**：给出仓库中记录代码写法的文档清单（例如 `AGENTS.md`），以及 code-review skill 中的 smell baseline 全文（该 subagent 没有其他途径拿到它）。要求它报告：改动违反成文规范的位置，并引用规范出处；命中的 smell，指明名称并引用对应改动。成文规范的违反属于明确问题，smell 一律属于判断，成文规范优先于 smell，工具已经强制检查的内容不再列出。

两个 verifier 都只拿到规格与改动范围，不附带你的实现思路。验证发现的问题全部修复之后重新验证，直至两个方向都没有问题。

## 报告

把两份验证结论分别放在 `## 规格` 与 `## 标准` 之下呈报，禁止合并或者重新排序，因为两个方向各自成立，合并会让一个方向掩盖另一个方向。

报告改动清单、验证结果，以及两个方向各自的问题总数与最严重的问题。
